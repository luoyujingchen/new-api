# 子业务公司与部门管理 PRD

## 元信息

- 需求标识：`sub-business-company-department-management`
- 文档目的：为 AI 或开发者完整实现该需求提供明确需求边界
- 范围说明：仅描述当前需求范围，不包含未在本文明确列出的其他组织扩展能力

## 1. 背景

当前系统缺少正式的组织架构能力，管理员无法在后台维护“公司-部门-用户归属”关系。
为支持多子业务运营，需要新增子业务公司和部门管理能力，并允许把用户挂载到具体公司和部门下。

## 2. 目标

- 新增后台公司管理能力。
- 新增后台部门管理能力。
- 支持用户与公司、部门的组织归属维护。
- 在用户管理中展示公司和部门信息。
- 为后续组织维度的统计、权限和控制能力预留基础数据结构。

## 3. 非目标

- 不做普通用户视角的组织管理页面。
- 不做组织级权限体系。
- 不做审批流、汇报流或复杂人事流程。
- 不做组织级限流、组织级计费、组织级配额策略。
- 不做跨公司移动部门。

## 4. 用户角色与权限

- `Root` 和 `Admin` 可以访问组织管理页面并调用相关接口。
- 普通用户不可见组织管理导航，不可访问组织管理路由。
- 公司、部门、用户归属相关后端接口必须全部走管理员鉴权。

## 5. 核心对象

### 5.1 公司 Company

字段：

- `id`
- `name`
- `code`
- `description`
- `status`
- `sort_order`
- `created_at`
- `updated_at`

衍生统计：

- `department_count`
- `user_count`

### 5.2 部门 Department

字段：

- `id`
- `company_id`
- `name`
- `parent_id`
- `level`
- `path`
- `description`
- `status`
- `sort_order`
- `created_at`
- `updated_at`

衍生统计：

- `child_count`
- `user_count`

关联展示：

- `company`
- `parent`

### 5.3 用户组织归属

用户增加两个可空字段：

- `company_id`
- `department_id`

用户返回体可带：

- `company` 摘要信息
- `department` 摘要信息

## 6. 业务规则

- 公司名称全局唯一。
- 公司编码全局唯一。
- 公司状态只允许 `1` 或 `0`，分别表示启用和禁用。
- 部门必须从属于某个公司。
- 部门是树状结构，最大层级深度为 4。
- 同一公司下、同一父部门下，部门名称不能重复。
- 根部门之间也视为同一父部门层级。
- 父部门必须属于同一公司。
- 部门不能移动到自己下面。
- 部门不能移动到自己的子孙部门下面。
- 部门移动后整体子树深度不能超过 4 级。
- 删除公司前，如果该公司下仍有部门或用户，则必须阻止删除。
- 删除部门前，如果该部门下仍有子部门或用户，则必须阻止删除。
- 设置用户部门时，如果只传部门不传公司，后端应自动补全该部门所属公司。
- 设置用户公司但不设置部门时，应只保留公司归属，并清空部门归属。
- 同时清空公司和部门时，视为清空用户组织归属。
- 编辑已有部门时，不允许变更所属公司。

## 7. 功能需求

### 7.1 公司管理

管理员可以：

- 分页查看公司列表。
- 按状态筛选公司列表。
- 查看公司详情。
- 创建公司。
- 编辑公司。
- 启用或禁用公司。
- 删除公司。
- 查看某个公司下的用户列表。
- 从公司页进入该公司的部门管理页。

公司列表至少展示：

- 公司名称
- 公司编码
- 描述
- 部门数量
- 用户数量
- 状态
- 操作

公司操作至少包含：

- 查看部门
- 启用/禁用
- 编辑
- 删除

### 7.2 部门管理

管理员可以：

- 分页查看部门列表。
- 按公司筛选部门列表。
- 按状态筛选部门列表。
- 获取某个公司的完整部门树。
- 查看部门详情。
- 创建根部门或子部门。
- 编辑部门基本信息。
- 移动部门到新的父部门下。
- 启用或禁用部门。
- 删除部门。
- 查看某个部门下的用户列表。

部门列表至少展示：

- 部门名称
- 层级
- 所属公司
- 描述
- 用户数量
- 状态
- 操作

部门名称应按层级进行缩进显示。

部门行操作至少包含：

- 添加子部门
- 启用/禁用
- 编辑
- 删除

当部门已位于第 4 级时，不再提供“添加子部门”入口。

### 7.3 用户组织归属管理

管理员可以：

- 在用户列表中看到用户所属公司和部门。
- 在用户编辑抽屉中设置公司。
- 在用户编辑抽屉中设置部门。
- 清空用户的公司与部门归属。

交互要求：

- 公司和部门字段均为可选。
- 更换公司时必须清空已选部门。
- 未选择公司时，部门下拉应禁用。
- 部门下拉只加载当前所选公司下的部门。
- 部门选项需体现层级缩进。

## 8. 前端页面要求

### 8.1 导航与路由

- 在后台 `Admin` 导航组下新增 `Organization Management`。
- 其下至少包含两个入口：`Companies`、`Departments`。
- 新增受保护路由前缀 `/organizations`。
- 访问 `/organizations` 默认跳转 `/organizations/companies`。
- 非管理员访问时跳转 `403`。

### 8.2 公司页

- 页面标题：`Companies`
- 说明文案：管理子业务公司
- 默认分页大小：20
- 提供“新建公司”按钮
- 支持创建抽屉和编辑抽屉
- 删除前二次确认
- 创建、编辑、删除、启停后刷新列表并给出提示
- 点击“查看部门”跳转到 `/organizations/departments?company_id={id}`

### 8.3 部门页

- 页面标题：`Departments`
- 默认分页大小：20
- 提供“新建部门”按钮
- 支持创建抽屉和编辑抽屉
- 当 URL 带 `company_id` 时，仅展示该公司的部门
- 有公司筛选上下文时，应显示当前公司名与清除筛选入口
- 创建、编辑、删除、启停后刷新列表并给出提示

### 8.4 公司表单

字段：

- `name`，必填，最大 128
- `code`，必填，最大 32
- `description`，可选，最大 500
- `status`，必填，取值 `0/1`
- `sort_order`，整数，默认 0

### 8.5 部门表单

创建时字段：

- `company_id`
- `name`
- `parent_id`
- `description`
- `status`
- `sort_order`

编辑时至少支持：

- `name`
- `parent_id`
- `description`
- `status`
- `sort_order`

规则：

- 编辑时 `company_id` 只读，不允许切换。
- `parent_id` 为空表示根部门。
- 父部门列表只展示当前公司内的部门。
- 父部门候选应排除当前部门自身。
- 如果前端允许在编辑时变更 `parent_id`，则必须正确调用独立移动接口，不能让修改 silently ignored。

## 9. 后端接口

### 9.1 公司接口

```text
GET    /api/company
GET    /api/company/all
GET    /api/company/:id
POST   /api/company
PUT    /api/company/:id
DELETE /api/company/:id
PATCH  /api/company/:id/status
GET    /api/company/:id/users
```

### 9.2 部门接口

```text
GET    /api/department
GET    /api/department/all
GET    /api/department/tree
GET    /api/department/:id
POST   /api/department
PUT    /api/department/:id
DELETE /api/department/:id
POST   /api/department/:id/move
PATCH  /api/department/:id/status
GET    /api/department/:id/users
```

### 9.3 用户归属接口

```text
PUT    /api/user/:id/department
DELETE /api/user/:id/department
```

## 10. 请求与返回约定

- 列表接口返回 `items`、`total`、`page`、`page_size`。
- 公司列表支持可选 `status` 过滤。
- 部门列表支持可选 `company_id` 与 `status` 过滤。
- 公司列表默认按 `sort_order ASC, id ASC` 排序。
- 部门列表必须保证树形顺序正确，即父部门始终出现在子部门之前；同层节点再按 `sort_order ASC, id ASC` 排序。实现方式不限，可基于 `path` 等层级字段保证该顺序。
- 公司详情和列表项应返回部门数与用户数。
- 部门详情和列表项应返回子部门数与用户数。
- 部门树接口必须要求 `company_id`。

## 11. 数据与迁移要求

- 新增 `Company` 表。
- 新增 `Department` 表。
- `User` 表新增 `company_id`、`department_id` 两个可空字段。
- `Department.level` 与 `Department.path` 由后端自动维护。
- 新模型必须纳入统一自动迁移流程。

## 12. 实现约束

- 不要改动现有用户创建/更新接口的主语义，组织归属通过独立接口补充更新。
- 新增页面文案至少补齐中英文。
- 不要把组织限流、组织计费等后续能力并入本次实现。

## 13. 验收标准

1. 管理员可以看到组织管理入口，普通用户无法访问。
2. 管理员可以创建公司并在列表中看到结果。
3. 重复公司名称或编码会被阻止并提示原因。
4. 公司列表能展示部门数和用户数。
5. 点击公司“查看部门”能跳转到带公司筛选的部门页。
6. 管理员可以在某个公司下创建根部门和子部门。
7. 超过 4 级的部门创建或移动会被阻止。
8. 同一父部门下的同名部门会被阻止。
9. 部门列表中的名称会按照层级缩进显示。
10. 部门列表中的父子顺序正确，父部门始终位于其子部门之前。
11. 编辑部门时不能切换所属公司。
12. 若支持在编辑中改父级，则改父级必须真正生效。
13. 从已有部门行可以直接发起“添加子部门”；对第 4 级部门不提供该入口。
14. 公司下还有部门或用户时无法删除公司。
15. 部门下还有子部门或用户时无法删除部门。
16. 用户列表中能看到公司列和部门列。
17. 编辑用户时，选择公司后部门下拉会联动到对应公司范围。
18. 清空公司和部门后，用户组织归属会被清空。
19. 只传部门不传公司时，后端会自动补全用户所属公司。
20. 传入与公司不匹配的部门时，后端会拒绝保存。
