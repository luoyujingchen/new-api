# 组织级共享时段 RPM 限流 PRD

## 元信息

- 需求标识：`organization-shared-time-slot-rpm-limits`
- 文档目的：为 AI 或开发者完整实现该需求提供可执行的产品与技术边界
- 范围说明：仅描述当前需求范围；除文中明确列出的附带修复外，不包含其他扩展能力

## 1. 背景

当前系统已有全局和分组维度的模型请求限流，但缺少组织维度的共享限流能力。

当多个用户属于同一部门或同一公司时，业务需要让他们共享一个按时间段生效的 RPM 配额，而不是每个用户各自独立限流。典型场景包括：

- 工作时间内限制某部门对高成本模型的总请求速率。
- 不同时段使用不同 RPM 配额。
- 某子部门需要比父部门更严格或更细粒度的限流规则。
- 某模型需要单独限流，其他模型沿用通配规则。

## 2. 目标

- 为公司和部门新增“组织级共享 RPM 规则”能力。
- 支持按时间段、按星期、按模型配置 RPM。
- 支持多条规则并按优先级匹配。
- 支持部门规则优先于公司规则。
- 支持子部门优先于祖先部门。
- 在现有 relay / playground 请求链路中实际生效。
- 在后台组织管理页提供规则配置 UI。

## 3. 非目标

- 不做组织级配额、计费或扣费策略。
- 不做按用户自定义组织 RPM。
- 不做普通用户可见的配置页面。
- 不做审批流、规则发布流程或灰度系统。
- 不做复杂冲突诊断页面。
- 不把已有 group/global 限流逻辑完全重写为组织逻辑。

## 4. 用户角色与权限

- `Root` 和 `Admin` 可以配置公司或部门的 RPM 规则。
- 普通用户不能查看或管理这些规则。
- 组织 RPM 管理 API 全部走管理员鉴权。
- 运行时限流对所有命中 relay / playground 请求的用户自动生效，无需额外用户权限配置。

## 5. 核心概念

### 5.1 组织规则对象

规则统一使用一个组织限流对象，既可绑定公司，也可绑定部门。

字段：

- `id`
- `org_type`，取值 `company` 或 `department`
- `org_id`
- `model_id`，可空
- `model_name`，可空
- `time_slots`
- `rpms`
- `priority`
- `status`
- `created_at`
- `updated_at`

### 5.2 时间段 TimeSlot

每条规则可包含一个或多个时间段，每个时间段对应一个 RPM 值。

字段：

- `start_time`，格式 `HH:MM`
- `end_time`，格式 `HH:MM`
- `weekdays`，取值 `0-6`，其中 `0=Sunday`

规则：

- `weekdays` 为空表示每天生效。
- `start_time <= end_time` 时表示普通日内时段。
- `start_time > end_time` 时表示跨天时段，例如 `23:00-02:00`。
- 跨天时段的凌晨部分仍归属于“起始日”的 weekday 规则。

### 5.3 共享限流语义

组织规则一旦命中，请求使用“组织级共享计数桶”，而不是用户个人限流键。

这意味着：

- 同一部门下所有用户共享同一个部门 RPM 限额。
- 同一公司下所有用户共享同一个公司 RPM 限额。
- 若规则带模型名，则共享键还会按模型维度区分。

## 6. 业务规则

### 6.1 规则归属

- 规则可挂在公司或部门上。
- `org_type=company` 时，`org_id` 必须对应有效公司。
- `org_type=department` 时，`org_id` 必须对应有效部门。

### 6.2 模型匹配

- 规则可指定某个模型，也可留空表示匹配所有模型。
- 若请求模型名与规则模型名完全一致，则视为精确匹配。
- 精确匹配优先于通配规则。
- 若同时传 `model_id` 与 `model_name`，两者必须能对应到同一模型元数据。
- 若仅传 `model_id`，后端应尝试回填对应的 `model_name`。
- 若仅传 `model_name` 且能在模型元数据中查到，则后端应尽量回填 `model_id`。
- 若仅传 `model_name` 但模型元数据中不存在，仍允许保存为按名称精确匹配的规则。
- 现有规则编辑时不允许切换模型范围。

### 6.3 时间段与 RPM

- 一条规则至少包含一个时间段。
- `time_slots` 与 `rpms` 的长度必须完全一致。
- 每个 RPM 必须大于等于 0。
- 当某个时间段对应的 RPM 为 `0` 时，该时段不应作为有效组织规则命中。
- 时间格式必须严格符合 `HH:MM`，小时 `0-23`，分钟 `0-59`。
- `weekdays` 中每个值必须在 `0-6` 范围内。

### 6.4 匹配优先级

运行时规则匹配顺序必须为：

1. 当前用户所属部门。
2. 当前部门的父部门。
3. 更高层祖先部门，逐级向上。
4. 当前用户所属公司。
5. 若没有命中任何组织规则，则继续走系统原有的 group/global 限流逻辑。

补充规则：

- 组织层级优先级高于规则 `priority`。
- 在同一组织内，精确模型规则优先于通配规则。
- 在同一组织、同一模型匹配范围下，按 `priority DESC, id ASC` 顺序匹配。
- 只有当前时间命中对应 `time_slot` 且该槽位 RPM 大于 0 时，规则才算生效。

### 6.5 状态与缓存

- 仅启用状态的规则参与运行时匹配。
- 组织规则需要有服务端缓存，以减少每次请求的数据库查询。
- 创建、更新、删除规则后必须立即使对应组织的缓存失效。

## 7. 功能需求

### 7.1 后台规则管理

管理员可以：

- 查看某个公司下的 RPM 规则列表。
- 查看某个部门下的 RPM 规则列表。
- 创建公司级 RPM 规则。
- 创建部门级 RPM 规则。
- 编辑现有规则的时间段、RPM、优先级、状态。
- 删除规则。
- 查看单条规则详情。

### 7.2 生效规则查询

管理员可以通过接口查询某个用户当前命中的组织 RPM 规则，用于调试和排查。

返回信息至少包含：

- 来源类型 `source`
- 组织名称 `org_name`
- 组织类型 `org_type`
- 组织 ID `org_id`
- 当前命中的 `time_slot`
- 当前生效 `rpm`
- 当前星期 `weekday`
- 命中的模型信息（如有）

若未命中组织规则，应返回 `source=none`，表示后续仍由既有 group/global 逻辑接管。

### 7.3 运行时接入

组织规则必须接入现有模型请求限流中间件，并在以下流量中生效：

- 用户 playground 请求
- 主要 relay v1 请求
- Gemini relay 请求

当组织规则命中时：

- 它优先于原有 group/global 的请求数设置。
- 运行时总请求数限制和成功请求数限制都应采用该规则的 RPM 值。
- 计数键应切换为组织级共享键，而不是用户级键。

## 8. 前端要求

### 8.1 页面入口

- 公司管理页的每行操作新增 `Configure RPM`。
- 部门管理页的每行操作新增 `Configure RPM`。
- 点击后打开组织 RPM 配置抽屉，不跳转独立页面。

### 8.2 规则抽屉

抽屉至少展示：

- 当前组织名称
- 当前组织类型 `Company` / `Department`
- 当前规则总数
- “Add RPM rule” 按钮
- 规则列表

规则卡片至少展示：

- 模型名称或 `All Models`
- 优先级
- 状态
- 每个时段的星期范围、开始/结束时间、RPM

规则卡片操作至少包含：

- 编辑
- 删除

### 8.3 规则表单

创建规则时支持：

- 选择模型名，或留空表示 `All Models`
- 设置 `priority`
- 设置 `status`
- 配置一个或多个时段

每个时段至少包含：

- `start_time`
- `end_time`
- `weekdays`
- `rpm`

交互要求：

- 至少保留一个时段。
- 支持新增时段。
- `weekdays` 留空表示每天生效。
- 创建时可选择模型或输入自定义模型名。
- 编辑时模型不可变更，只读展示。
- 删除规则前需要确认。
- 创建、编辑、删除后刷新抽屉列表并提示结果。

## 9. 后端接口

```text
GET    /api/rate-limit
POST   /api/rate-limit
GET    /api/rate-limit/:id
PUT    /api/rate-limit/:id
DELETE /api/rate-limit/:id
GET    /api/rate-limit/user/:id
```

### 9.1 查询规则列表

请求参数：

- `org_type`，必填，`company | department`
- `org_id`，必填
- `model_id`，可选
- `status`，可选

返回：

- `items`
- `total`

### 9.2 创建规则

请求体：

```json
{
  "org_type": "department",
  "org_id": 123,
  "model_id": 1,
  "model_name": "gpt-4o",
  "time_slots": [
    {
      "start_time": "09:00",
      "end_time": "18:00",
      "weekdays": [1, 2, 3, 4, 5]
    }
  ],
  "rpms": [60],
  "priority": 10,
  "status": 1
}
```

### 9.3 更新规则

更新范围仅包含：

- `time_slots`
- `rpms`
- `priority`
- `status`

不允许通过更新接口切换规则归属或模型归属。

### 9.4 查询用户当前生效规则

请求参数：

- 路径参数 `:id` 为用户 ID
- 可选 `model_name`
- 可选 `model_id`

返回体中的 `source` 允许值：

- `department`
- `company`
- `group`
- `global`
- `none`

本次提交要求至少正确返回：

- `department`
- `company`
- `none`

## 10. 数据模型与存储要求

- 新增 `OrganizationRateLimit` 表。
- `time_slots` 与 `rpms` 使用 JSON 序列化存储。
- 新模型必须纳入统一数据库自动迁移流程。
- 若存在历史只保存 `model_id` 的规则，应提供 `model_name` 回填逻辑。

## 11. 技术约束

- 运行时限流继续复用现有模型请求限流中间件，不新增并行限流链路。
- 组织规则缓存必须有明确失效机制。
- 新增文案至少覆盖项目支持的前端语言文件。

## 12. 验收标准

1. 管理员可以在公司页和部门页看到 `Configure RPM` 入口。
2. 管理员可以为公司创建共享 RPM 规则。
3. 管理员可以为部门创建共享 RPM 规则。
4. 一条规则可以配置多个时间段，每个时间段有独立 RPM。
5. `weekdays` 留空时，规则每天生效。
6. 跨天时段例如 `23:00-02:00` 能正确命中次日凌晨。
7. 跨天时段的凌晨匹配应沿用起始日 weekday 语义。
8. 非法 weekday 或非法时间格式会被拒绝。
9. 精确模型规则优先于同组织下的通配规则。
10. 当前部门规则优先于父部门规则。
11. 父部门规则优先于公司规则。
12. 当没有组织规则命中时，系统继续使用原有 group/global 限流逻辑。
13. 命中组织规则后，同一组织下多个用户共享同一个 RPM 计数键。
14. 创建、更新、删除规则后，缓存会被正确失效。
15. 编辑规则时不能修改模型归属。
16. 查询用户当前生效规则接口能返回部门、公司或 none 三种结果。
