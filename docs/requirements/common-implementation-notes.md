# 公共实现注意项

这份文档用于沉淀可跨多个需求包复用的实现注意事项。

原则：

- 只有“脱离具体业务名词后仍然成立”的约束，才适合上收为公共注意项。
- 如果某条内容换一个需求依然基本不变，优先放到这里。
- 如果某条内容一旦移除就会改变当前需求的功能边界、用户路径、字段语义或验收结果，则必须留在对应 PRD/prompt 中。
- 单个 implementation prompt 可以在开头直接引用本文件，用于替代重复的仓库约束、通用前端实现约束和通用验证模板。

## 1. 适合上收的内容

### 1.1 仓库级技术约束

这类内容通常不属于某一个需求本身，而是整个仓库的实现前提：

- 后端分层结构约束，如 `Router -> Controller -> Service -> Model`
- 优先使用 GORM，避免无必要原生 SQL
- 数据库兼容性要求，如同时兼容 SQLite、MySQL、PostgreSQL
- JSON 编解码需遵循仓库公共封装
- 前端默认使用 Bun、TanStack Router、React Query、现有 i18n 体系

这些内容除非当前需求对其中某一条有额外强化，否则不必在每个 PRD/prompt 中重复展开。

### 1.2 通用前端实现约束

这类内容常来自当前前端架构本身，而不是某个业务需求：

- 站内跳转应使用前端路由能力，不要用会触发整页重载的方式
- 复用现有共享页面布局、表格、抽屉、筛选栏模式，不要假设未验证的共享组件 API
- 若新增表单字段，要同步更新 schema、默认值、回填逻辑和提交转换逻辑
- 若页面已存在 URL 状态或查询参数模式，应沿用现有模式而不是重新发明一套

这些属于“如何在本仓库里正确落地”的公共注意项，通常不应该被写成某个需求独有的业务要求。

### 1.3 通用验证要求

以下内容通常也应视为公共要求：

- 优先运行最小范围的编译、类型检查、测试或页面流程验证
- 无法验证时明确说明未验证项与原因
- 尽量汇报行为级验证结果，而不是只说“已修改代码”

这类内容可以在单个 prompt 中简写，没必要每次重复展开为大段模板。

### 1.4 通用文档写作约束

- PRD/prompt 默认不锚定具体 commit
- 不假设已有实现一定存在
- 不假设后续实现已经被读者知晓
- 如需前置依赖，只做最小化说明

## 2. 不应上收的内容

以下内容通常必须保留在对应需求包中，因为它们直接定义当前需求本身：

- 当前需求的业务对象、字段、状态值、接口路径
- 当前需求独有的用户路径、页面入口、交互动作
- 会影响用户可见行为的排序、优先级、匹配规则、联动规则
- 当前需求独有的异常处理语义和拒绝条件
- 当前需求独有的验收标准

示例：

- “部门列表必须保证父部门显示在子部门之前”应留在组织管理需求里，因为它直接定义该需求的可见结果。
- “部门行必须提供添加子部门入口”也应留在组织管理需求里，因为它属于该需求特有的交互要求。
- “站内导航不要使用整页刷新”更适合作为公共注意项，因为它对多个后台页面都成立。
- “不要为共享布局组件假设未经验证的 prop API”也更适合作为公共注意项，因为它是共享组件使用原则，不是单一业务规则。

## 3. 一个简单判断标准

可以用下面三个问题快速判断是否应上收：

1. 这条内容换到别的需求里，是否基本不用改字面表述？
2. 这条内容描述的是仓库实现方式，而不是当前业务结果吗？
3. 把这条内容从当前 PRD 删除后，是否不会改变该需求的功能边界，只会减少实现偏差？

如果三个问题大多回答“是”，通常适合上收为公共注意项。

## 4. 当前建议上收的条目

基于现有需求包，建议优先上收这些公共注意项：

- 仓库级后端分层、GORM、JSON 封装、跨数据库兼容约束
- 前端站内导航必须走 TanStack Router，不做内部页面硬跳转
- 复用现有共享布局和通用组件模式，不凭空假设 props API
- 表单字段新增后同步 schema / defaultValues / reset / payload 转换
- 默认使用现有 React Query、列表、抽屉、筛选和 URL 状态模式
- 实现后做最小范围验证，并汇报未验证项

## 5. 当前建议继续留在单需求中的条目

以下内容仍应只放在具体需求里：

- 树形列表必须按父子顺序展示
- 某类行操作是否必须出现，例如“添加子部门”
- 某个 header、字段、状态或匹配规则的业务语义
- 某个筛选条件、联动逻辑、优先级规则
- 某个功能必须支持的页面入口、列表列和验收点
